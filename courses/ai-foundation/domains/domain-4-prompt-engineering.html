Prompt Engineering Fundamentals

The highest-leverage practical skill: constructing effective prompts and improving weak ones.

Learning outcomes

By the end of this domain, candidates will be able to:

  • Construct a prompt using the four components: task, context, format and constraints
  • Assign a role or persona and name the audience to shape register and depth
  • Distinguish zero-shot from few-shot prompting and know when to use examples
  • Request structured output and decompose a complex task into ordered steps
  • Treat first output as a draft and refine through specific, corrective follow-ups
  • Diagnose and correct vague, overloaded, leading, unformatted and one-and-done prompts

What this subject is about

What this domain covers, with teaching notes area by area.

4.1, Anatomy of a prompt

Every effective prompt can be labelled with four components. Task: what you want done. Context: what the model needs to know to do it well. Format: how the output should look, table, bullets, headed sections, length. Constraints: limits and rules, length, tone, exclusions, audience. Strong prompts contain all four; weak prompts omit them. Example: \"Write a 300-word introduction to networking for new apprentices\" labels task (write an introduction), context (networking), format (300 words), and audience (new apprentices).

4.2, Role & audience

A persona shapes the stance the model takes; a named audience shapes register and depth. \"As a technical reviewer, for the board\" produces different output from \"as a coach, for apprentices\", same facts, different depth, different vocabulary. The test: would the intended reader understand the output? If not, re-target the role or audience.

4.3, Few-shot prompting

Zero-shot: no examples given. Few-shot: one or more examples attached, calibrating style, format and tone. The deciding rule (slide 10): use examples whenever the output must match a pattern, a meeting agenda, a report structure, a particular tone. The course compares the two directly; know when each is appropriate.

4.4, Structure & decomposition

Request structured output explicitly, tables, headed sections, bullets, numbered steps, and the model delivers work product rather than prose. For complex tasks, decompose: split into ordered steps, ask for a plan first, execute step by step, review each. Decomposition tames complexity; plans before execution improve quality.

4.5, Iterative refinement

The first output is a draft, not an answer. Refine with specific, corrective follow-ups, \"shorten the second paragraph\", \"retone for a non-technical reader\", \"turn the middle section into a table\", one change at a time. \"Make it better\" fails because it gives the model nothing to act on. Prompting is a conversation that converges.

4.6, Common prompting faults

Five faults, each with a repair: vague (no explicit task, state what you want done); overloaded (too many asks at once, split them); leading (suggests the answer, ask neutrally and let evidence decide); unformatted (no format requested, specify it); one-and-done (no refinement, treat the output as a draft). Diagnose, name, repair, re-test.
