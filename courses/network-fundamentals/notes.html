Session 1: Network Foundations: Networking Models & IP Addressing

Your revision guide for Session 1, the first of three network-foundation sessions in the combined course. Read alongside the slides, work the calculations by hand, then use the self-check questions and the session quiz to confirm you are ready for the security content ahead.

Core concepts

1A — Network models

The OSI model's seven layers are the exam's reference grid: application (7), presentation (6), session (5), transport (4), network (3), data link (2), physical (1). The TCP/IP stack condenses these to four: application (OSI 5–7), transport (4), internet (3), network access (1–2). Encapsulation builds the PDU — data becomes a segment (transport header + port), a packet (IP header), then a frame (Ethernet header + MACs). Firewalls read layer 3/4 fields; WAFs work at layer 7.

1B — IPv4 addressing

An IPv4 address is 32 bits in four octets, split into network and host portions by the mask. Classful addressing (A–E) wasted space; CIDR lets the boundary fall anywhere. Two formulas carry subnetting: subnets = 2^n (n = borrowed bits); usable hosts = 2^h − 2 (h = host bits). The network and broadcast addresses are never assignable.

1C — VLSM

VLSM uses different masks inside one network to match real requirements. Always allocate the largest requirement first, and never overlap. In security terms, each subnet becomes a zone: DMZ, internal servers, management, workstations. Segmentation is the blast-radius control: it limits lateral movement, so a compromised workstation cannot reach the server subnet. A DMZ is a buffer between the internal network and the internet, holding only public-facing services and firewalled on both sides. Network attacks such as VLAN hopping and on-path attacks succeed only when this segmentation fails, so an unbroken zone design is itself a defence.

1D — IPv6

IPv6 is 128 bits in eight hex groups. Shorten by dropping leading zeros and using one double colon for a contiguous zero run. Address types: global unicast (2000::/3), link-local (fe80::/10), unique local (fc00::/7), multicast (ff00::/8). There is no broadcast. Dual-stack operation, running IPv4 and IPv6 together, enlarges the attack surface, because every additional entry point is a way in for an attacker. IPv6 traffic can bypass IPv4-only ACLs, so filter both families.

Practical cautions

  • Do not assign the network or broadcast address to a host.
  • Do not allocate VLSM smallest-first — it fragments the address space.
  • Do not ignore segmentation as a security control: it contains breaches and blocks lateral movement.
  • Do not assume a /24 means 254 usable hosts in every context — it is 254 only as one subnet.
  • Do not use two double colons in an IPv6 address — one per address only.
  • Do not ignore IPv6 traffic in monitoring — it can bypass IPv4-only filters.

Session 2: Switching, VLANs & Network Architectures

Your revision guide for Session 2, the second of three network-foundation sessions. Read alongside the slides, trace the frame walkthrough by hand, then use the self-check questions and the session quiz to confirm you are ready for the services session and the Security+ core. The running theme is segmentation: each VLAN and each zone is a containment boundary, and the exam treats segmentation as an architectural control.

Core concepts

2A — Layer 2 switching

Switches forward frames at layer 2 using MAC addresses. On receipt: learn the source MAC and port, look up the destination, forward to the matching port — or flood if unknown. Broadcasts always flood. CAM-table overflow (MAC flooding) degrades a switch into hub mode, letting an attacker see all frames on the segment.

2B — VLANs & trunking

VLANs segment one physical switch into logical broadcast domains — the core containment control. Trunk ports carry tagged frames between switches via 802.1Q; access ports carry one untagged VLAN. Segmentation reduces the attack surface, contains blast radius and blocks lateral movement. The default native VLAN (VLAN 1) is an attack surface — change it, prune unused VLANs and restrict trunk allowed lists. VLAN hopping crosses boundaries by switch spoofing (negotiating a trunk) or double tagging (native VLAN spoof). Microsegmentation takes this further, isolating individual workloads via SDN.

2C — Spanning Tree

Redundant links create loops; STP blocks redundant ports for a loop-free topology. The root bridge is the lowest bridge ID; each non-root switch picks the lowest-cost root port. Ports are blocking, listening, learning, forwarding or disabled. RSTP (802.1w) converges in seconds. BPDU Guard and Root Guard stop rogue-root attacks, and port security limits MACs per port.

2D — Architectures

Segments become security zones: DMZ for public services, bracketed by external and internal firewalls with a proxy between; management isolated; workstations separate from servers; unmanaged IoT devices on their own segment. A campus has access, distribution and core layers. Segmentation limits blast radius and blocks lateral movement — containment is an architectural control that the exam treats across Domain 3 and Domain 4.

Practical cautions

  • Do not confuse switches (layer 2, frames) with routers (layer 3, packets).
  • Do not leave the native VLAN at VLAN 1 — it is a known attack surface.
  • Do not assume VLANs make the network faster — they make it segmented.
  • Do not confuse BPDU Guard (shuts the port) with Root Guard (stops root takeover).
  • Do not ignore unknown-unicast floods in a capture — they may be MAC flooding.
  • Do not confuse VLAN hopping methods: switch spoofing negotiates a trunk; double tagging spoofs the native VLAN.
  • Do not treat segmentation as only separating departments — it is a lateral movement and blast radius control.

  • Learn, look up, forward, flood — the switch behaviour sequence is a classic question.

Session 3: Network Services & the Attack Surface

Your revision guide for Session 3, the final session of the network-foundation strand. Read alongside the slides, run the commands on any Linux box you can reach, then use the self-check questions and the session quiz to confirm you are ready for the Security+ core.

Key terms

TermDefinition
DNSTranslates names to addresses — the internet's directory
A / AAAA recordName to IPv4 / name to IPv6
CNAMEAlias for another name
MX recordMail exchange server for a domain
TXT recordSPF, DKIM, DMARC text records

DNSSECCryptographic signing of DNS responses
DHCP DORADiscover, Offer, Request, Ack — the address assignment process
T1 / T2 timersLease renewal at 50% / rebind at 87.5%
Rogue DHCP serverUnauthorised server assigning malicious settings

DHCP snoopingSwitch filter trusting only authorised DHCP ports
NTPNetwork Time Protocol — clock synchronisation, UDP 123
StratumDistance from the authoritative time source
SSHEncrypted remote access replacing Telnet — TCP 22
Key-based authPublic key stored on the server; private key proves possession
Attack surfaceThe sum of entry points an attacker can use to enter or extract data
Threat vectorThe path or method an attacker uses to reach the attack surface

Core concepts

3A — DNS

DNS hierarchy: root, TLD, authoritative, recursive resolver. Record types: A, AAAA, CNAME, MX, NS, TXT, PTR. Attacks: cache poisoning (forged answers redirect users), tunnelling (data inside queries), amplification (spoofed small queries, huge responses). DNSSEC signs responses so forgery fails. Recursive resolvers should be restricted to internal clients — an open resolver is a public amplification tool that widens the attack surface. Distinguish spoofing (forging one reply) from poisoning (planting it in the cache for all users).

3B — DHCP

DORA: Discover, Offer, Request, Ack. T1 at 50% of lease triggers unicast renewal; T2 at 87.5% triggers broadcast rebind. Attacks: rogue servers assign malicious gateways/DNS (a man-in-the-middle chain); starvation exhausts the pool. Defence: DHCP snooping builds a MAC-to-IP-to-port binding table on the switch, and segmentation contains a rogue server to one segment.

3C — NTP

Stratum 0 atomic/GPS sources, stratum 1 servers, stratum 2 onward. UDP 123. Attacks: amplification via monlist (up to 100× response), spoofing to shift time. Mitigations: authenticated NTP (NTS), restricted access. Forensic rule: verify clock offset before acquiring evidence — minutes of offset corrupt timelines. Wrong clocks also break Kerberos ticket validation, so accurate time is infrastructure, not a convenience.

3D — SSH

TCP 22. Key exchange derives a shared session key without transmission. Key-based auth beats passwords — keys are never sent and resist brute force. Hardening: PermitRootLogin no, PasswordAuthentication no, LogLevel VERBOSE, AllowUsers, ClientAliveInterval. Verification: ss -tnp, journalctl -u ssh, grep sshd /var/log/auth.log. Hardening shrinks the attack surface: disabling password auth removes brute force as a threat class, and restricting users denies everyone else.

Practical cautions

  • Do not run an open recursive DNS resolver — it is a public amplification tool.
  • Do not leave the native VLAN or DHCP ports unguarded — both are entry points.
  • Do not trust a forensic timeline from a system whose clock was never verified.
  • Do not use password authentication for SSH when keys are available.
  • Do not ignore unexpected listening ports in ss -tuln — that is how compromise shows.
  • Do not let unnecessary services run — each one widens the attack surface.

Self-check questions

  1. What is the purpose of the T1 timer in DHCP?
  2. What is the difference between an authoritative DNS server and a recursive resolver?
  3. How does DNS cache poisoning work, and what stops it?
  4. How does NTP amplification work?
  5. Why is key-based SSH authentication more secure than passwords?
  6. What command shows all listening TCP and UDP services on Linux?
  7. How does closing unused services reduce the attack surface?

Answers are in your session slides

If you cannot answer a self-check from memory, revisit the corresponding slide, then retake the quiz.

Exam tips for Session 3

  • DNSSEC stops poisoning; DHCP snooping stops rogue servers — match the control to the attack.
  • NTP amplification and DNS amplification are both DDoS scenarios — know the mechanism.
  • SSH hardening settings appear in scenario questions — remember PermitRootLogin no.
  • The service-port table (22 SSH, 53 DNS, 67/68 DHCP, 123 NTP) is core knowledge.
  • Spoofing forges one reply; poisoning plants it in a cache — an exam-favourite distinction.
  • Reducing the attack surface is a stated security principle — closing unused services is an example.

Further reading

  • RFC 1034/1035 — DNS concepts and implementation.
  • RFC 2131 — DHCP.
  • RFC 5905 — NTPv4.

Session 4: Fundamental Security Concepts

Your revision guide for Session 4 (Lesson 1 · Domain 1, 12% of the exam). Read alongside the slides, then use the self-check questions and the session quiz to confirm you are exam-ready.

Key terms

TermDefinition
ConfidentialityInformation should only be read by authorised persons
IntegrityData is stored and transferred as intended; modification requires authorisation
AvailabilityInformation is accessible to those authorised to view or modify it
Non-repudiationPersons cannot deny creating or modifying data — proof of origin and action
AAAIdentification, authentication, authorisation, accounting
Gap analysisComparing current security posture against a target framework to find gaps

Operational controlDepends on a person to implement — training, guards
Technical controlImplemented in systems and software — firewalls, encryption
Physical controlMediates access to premises and hardware — locks, cameras

Least privilegeUsers receive only the access they need
Zero trustVerify every request — never trust implicitly

Core concepts

1A — Security concepts

The CIA triad is the foundation: confidentiality (read only by authorised persons), integrity (data stored and transferred as intended), availability (accessible when needed). Each pillar has distinct threats and controls: confidentiality is threatened by interception and data theft, protected by encryption and access controls; integrity by unauthorised tampering, protected by hashing and digital signatures; availability by denial of service and hardware failure, protected by redundancy, backups and failover. Non-repudiation adds proof of origin and action via digital signatures and audit logs. The AAA framework sequences access: identify, authenticate, authorise, account — authentication rests on three factors (something you know, have, or are). The NIST CSF functions — identify, protect, detect, respond, recover — structure a whole programme, and gap analysis scores maturity against it.

1B — Security controls

Controls are classified on two axes. Category: managerial (policies and risk assessments), operational (guard patrols, incident response), technical (firewalls, ACLs, IDS, encryption), physical (locks, fences, cameras, mantraps). Functional type: preventive (blocks before — firewalls, access controls), detective (finds during — IDS, log monitoring), corrective (fixes after — patching, restore), directive (guides behaviour — acceptable use policies), deterrent (discourages — warning banners, visible cameras), compensating (substitutes when a primary control is not feasible — enhanced logging in place of encryption).

1C — Roles & principles

CISO/CSO owns strategy; ISSO manages day-to-day; data owner is accountable; custodian implements; analyst monitors and responds; auditor verifies independently. Principles: defence in depth (layered controls so no single point of failure), least privilege (only the access needed), separation of duties (no one person controls a critical process alone), zero trust (never trust, always verify; microsegmentation and continuous verification; a design principle, not a product).

Memory aids

  • CIA — Read, Unchanged, Accessible: confidentiality is the read side, integrity the change side, availability the access side.
  • AAA — I A A A: the user is identified, then authenticated, then authorised, then accounted.
  • Controls on two axes: category asks who or what (managerial, operational, technical, physical); type asks when and how it acts (preventive to compensating).
  • Non-repudiation means deniable, no: signatures and logs make denial fail.
  • Zero trust — never trust, always verify: a design principle, not a product.

Practical cautions

  • Do not confuse integrity (unchanged) with correctness (true).
  • Do not confuse preventive (blocks) with deterrent (discourages).
  • Do not confuse the data owner (accountable) with the custodian (implementer).
  • Do not treat a vulnerability scan as a gap analysis — they measure different things.
  • Do not expect zero trust to be a product — it is a design principle.

Self-check questions

  1. Define the three pillars of the CIA triad and give one control for each.
  2. What does non-repudiation provide, and how?
  3. Name the four steps of the AAA framework and the three authentication factors.
  4. Give an example control for each of the four categories.
  5. Which functional type operates during an attack? Which after?
  6. What are the five NIST CSF functions?
  7. Explain the difference between a vulnerability scan and a gap analysis.
  8. Who is accountable for a data set, and who implements the controls that protect it?
  9. What does microsegmentation do in a zero-trust model?

  • Know the two-axis control model cold — category and functional type, with one concrete example for each.
  • Non-repudiation is a favourite exam term — link it to signatures and logs, not logging alone.
  • Learn the classic paired distinctions: preventive versus deterrent, integrity versus correctness, owner versus custodian, scan versus gap analysis.

Session 5: Threats, Attack Types & Threat Actors

Core concepts

2A — Threat actors

Risk = threat × vulnerability: a threat that exploits a vulnerability creates risk. Actors are compared by behaviour (targeted or opportunistic), source (internal or external), sophistication, resources and funding, and motivation with intent. Types: lone hackers, script kiddies, hacker teams and hacktivists, nation-state actors and APTs, organised crime, competitors, and insiders (malicious and unintentional). Motivations: financial, political or ideological, strategic, and personal.

2B — Attack surface & vectors

The attack surface spans hardware, software, networks, processes and human factors, and grows as cloud, mobile and IoT devices are added. Vectors: direct access (USB, console), remote access (VPN, RDP, SSH), wireless and cloud, open ports, lure-based (Trojan, malicious documents, phishing, spear phishing, whaling, smishing, vishing, watering holes), vulnerable software (unpatched systems, misconfigurations, zero-days, unsupported systems, default credentials), and the supply chain (compromised updates, vendor credentials). The attack chain: recon, vector, exploit, act.

Practical cautions

  • Do not call all hackers criminals; white hats are ethical.
  • Do not forget unintentional insiders; most insider incidents are accidents.
  • Do not use 'APT' for every advanced attack; persistence and strategy are the point.
  • Do not ignore the human vectors; phishing is the most common entry point.
  • Do not assume patching fixes everything; unsupported systems and zero-days have no patch.
  • Do not treat vulnerability and risk as the same thing; risk needs a threat behind the weakness.

  6. What are the four steps of the attack chain?

Session 6: Cryptography & Public Key Infrastructure

Your revision guide for Session 6 (Lesson 3 · cryptography objectives of Domain 2). Read alongside the slides, then use the self-check questions and the session quiz to confirm you are exam-ready. Everything hangs on two maps: the three-job map — encrypt, hash, sign — and the data-state map — at rest, in transit, in use.

Key terms

TermDefinition

PKIInfrastructure that proves the identity of a public key holder
Certificate authority (CA)Issues certificates to verified subjects

X.509The digital certificate standard

CRL / OCSPRevocation list / real-time online certificate status protocol
TPM / HSMMotherboard cryptoprocessor / dedicated hardware security module

Steganography / tokenisationConcealing in a cover file / substituting data with reversible tokens

Core concepts

3A — Cryptographic algorithms

Symmetric: one key, fast, bulk data, distribution problem. AES is the standard, with 128, 192 or 256-bit keys. Asymmetric: key pairs, solves distribution, slower, small payloads. RSA rests on factoring difficulty; ECC reaches similar strength with smaller keys, ideal for mobile and IoT. Key length: longer keys, larger keyspace, stronger against brute force. Hashing: one-way, fixed length, anti-collision and avalanche — integrity, not secrecy; SHA-256 or better, as MD5 and SHA-1 are broken. Digital signatures: hash + private key, verified with public key — integrity, authentication, non-repudiation.

3B — Public key infrastructure

CAs issue X.509 certificates binding public keys to identities; RAs verify identities before issuance. Trust flows from self-signed roots through intermediate CAs to leaf certificates, and trusting the root vouches for the whole chain. CSRs carry the public key (never the private key). CN is legacy; SAN is modern. Revocation: CRL lists vs OCSP real-time queries, part of the lifecycle of issuance, renewal, revocation and expiration. Key management: lifecycle, TPM/HSM cryptoprocessors, escrow with M-of-N control.

3C — Cryptographic solutions

Data at rest: full disk, file and database encryption. Data in transit: transport encryption (TLS, VPN) with perfect forward secrecy — an asymmetric handshake exchanges a symmetric session key, and ephemeral keys protect past traffic. Data in use: processed in memory. Passwords: salt + key stretching. Blockchain: blocks chained by hashes, tamper-evident. Obfuscation: steganography (least significant bits of images), tokenisation, data masking, code obfuscation.

Practical cautions

  • Do not use asymmetric for bulk data — symmetric is the bulk tool.
  • Do not rely on encryption for integrity — hashing does that job.
  • Do not treat a certificate as a safety rating — it proves key-to-identity binding.
  • Do not use MD5 or SHA-1 for anything modern — SHA-256 or better.
  • Do not store passwords without salt and stretching.
  • Do not confuse CRL with OCSP — one is a list, the other a real-time query.

  • Sign with private, verify with public — memorise the direction.
  • Data-state questions: at rest → disk/file; in transit → TLS/PFS.
  • Know CN vs SAN, CRL vs OCSP, TPM vs HSM — the exam loves pairs.
  • Recognise algorithms by role: AES symmetric, RSA and ECC asymmetric.
  • Remember salting defeats pre-computed tables; stretching raises guess cost.

Core concepts

4A — Authentication

Factors: know, have, are/do, somewhere. MFA requires different categories — password+PIN is one factor. Passwords: length over complexity, no hints, managers for uniqueness. Biometrics: FAR and FRR trade off. Hard tokens (smart card, OTP, FIDO) resist phishing; soft tokens (SMS, push, apps) are convenient but some are interceptable. Passwordless uses authenticator-held keys.

4B — Account policies & authorisation

Account types: user, privileged, service, shared, guest. Provisioning manages the user lifecycle — onboard, modify on role change, offboard promptly. Policies: lockout, time-of-day, auditing. Authorisation: permissions, least privilege, RBAC (roles), ABAC (attributes). Privileged accounts need PAM: just-in-time access, password vaulting and session recording. Identity governance reviews access, enforces policy and audits.

4C — SSO & federation

SSO: one authentication, many apps — removes password fatigue but concentrates risk, mitigated by MFA and monitoring. Directory services (Active Directory, LDAP) are the source of truth for identities. Federation: IdP authenticates and issues a token, SP trusts the assertion. Protocols: SAML (assertions), OAuth 2.0 (authorisation), OIDC (identity on OAuth), LDAP (directory), Kerberos (tickets).

Practical cautions

  • Do not count two knowledge factors as MFA.
  • Do not rely on SMS as a strong second factor — it is interceptable.
  • Do not force password expiry without reason — NIST favours length.
  • Do not give service accounts more privilege than the service needs.
  • Do not leave departed staff accounts active — offboard promptly.
  • Do not expose privileged accounts without PAM — use JIT and vaulting.
  • Do not deploy SSO without MFA and compromise-recovery plans.

Core concepts

8A — Architecture

Tiered (core/distribution/access), spine-leaf (data-centre fabric) and SMB (flat) models. Segmentation is containment: VLANs, the DMZ with twin firewalls, and microsegmentation confine a compromise. Least connectivity limits connections to what is necessary. The distribution layer enforces policy; the core only transports; redundancy removes single points of failure.

8B — Security appliances

Firewalls: stateless (per-packet), stateful (state table, connection-aware), NGFW (application-aware with deep packet inspection), UTM (all-in-one). IDS detects and alerts; IPS blocks inline; signature detection catches known attacks while anomaly detection finds deviations from a baseline. Proxy forwards/filters/caches and hides topology; WAF protects web apps; load balancers distribute with health checks; NAC enforces posture — allow, quarantine, deny — based on antivirus status, patches and credentials.

8C — Secure remote access

VPN types: site-to-site (often IPsec tunnel mode), remote access, client-based (often IPsec), SSL VPN (browser/TLS), split tunnel. RDP is high-risk — MFA, allowlists, patching, monitoring. Jump servers and bastion hosts give hardened administrative entry. ZTNA verifies per request; SASE delivers ZTNA + SD-WAN as a service.

8D — Secure protocols

TLS 1.2/1.3 current — SSL and TLS 1.0/1.1 deprecated; cipher suites; PFS. HTTPS = HTTP over TLS; validate chain, hostname, expiry, revocation against a trusted CA to defeat man-in-the-middle; HSTS. Toolkit: TLS/HTTPS for web, SSH/SFTP for admin and transfer, IPsec for VPNs, S/MIME for email, DNSSEC for DNS integrity, FTPS for secure file transfer.

Practical cautions

  • Do not confuse IDS (detects) with IPS (blocks inline).
  • Do not expect signature detection to find new attacks — anomaly detection covers the unknown.
  • Do not call TLS 1.0 acceptable — it is deprecated.
  • Do not assume a split tunnel protects all user traffic — it only covers the tunnel.
  • Do not put public services inside the internal segment — that is the DMZ's job.
  • Do not forget MFA on remote access — it is the non-negotiable control.
  • Do not treat a firewall's state tracking as encryption — filtering and encryption are separate.

Core concepts

9A — Endpoint security

The endpoint stack: AV/EDR (signature plus behaviour), hardening (baseline from CIS benchmarks or vendor guides, patching, disable unused services, ports and default accounts), application control (allowlisting over blocklisting, backed by code signing), MDM (enrol, configure, enforce, wipe) with application vetting and containers for BYOD, and OS controls, least privilege, secure boot, full disk encryption and firmware updates.

9B — Application lifecycle

Shift left: threat modelling before code, code review at every change, SAST for source and DAST for running apps. Secure coding keeps the code at least privilege, hides errors, and validates all input by whitelisting, sanitisation and boundary checks. DevSecOps puts security in the CI/CD pipeline and scans infrastructure as code, so secure code ships as fast as insecure code.

9C — Application attacks

SQL injection: input treated as code, fix with parameterised queries and input validation. XSS: script in another user's browser, fix with output encoding; a Web Application Firewall filters web traffic. CSRF: forged action on a session, fix with tokens and same-site cookies. Also buffer overflow, directory traversal and race conditions, mitigated by input validation, least privilege and sandboxing.

9D — Cloud & virtualisation

Service models: IaaS (you secure everything above the hypervisor), PaaS (you secure the app and its data), SaaS (the vendor secures nearly everything). Deployment models, public, private, hybrid and community, shift the line. Shared responsibility: vendor secures the cloud, you secure what is in it. Misconfiguration is the top cloud risk, managed with CASB and posture management. Virtualisation: the hypervisor is the crown jewel, Type 1 beats Type 2, VM escape is the nightmare, containers share the kernel and need namespaces and seccomp.

Practical cautions

  • Do not rely on antivirus alone, signatures miss unknown threats.
  • Do not choose blocklisting over allowlisting for unknown threats.
  • Do not skip input validation, every field is a potential injection point.
  • Do not confuse XSS (hijacks the browser) with CSRF (hijacks the action).
  • Do not assume the cloud vendor secures your data and configuration.
  • Do not assume private cloud has no shared responsibility, duties are still divided.
  • Do not treat all hypervisors as equal, a Type 1 bare-metal hypervisor is safer than Type 2.
  • Do not treat containers as perfectly isolated, they share the kernel.

Core concepts

10A–10D · The vulnerability loop

Identify: network scanners see the attack surface, host agents see installed truth, and credentialed scans use valid credentials to reveal missing patches and misconfiguration. Feeds such as CVE and the NVD keep tooling current. Assess: CVSS gives a severity score from base, temporal and environmental metrics, but severity is not risk. Risk adds exploitability, exposure and asset criticality, and false positives must be validated before acting. Remediate: patch first, change configuration to reduce the surface, compensate second, and accept the risk with a documented owner and date last. Report and disclose: SLAs by severity, metrics and trends in the report, responsible disclosure to the vendor, and a pentest only under written rules of engagement. Validate by rescanning.

10E · Resiliency

Redundancy removes single points of failure: RAID storage, NIC teaming, dual power supplies, load balancing and automatic failover. Availability is measured as uptime and mean time between failures. Backup types: full (simplest restore), incremental (fast backup, slow chain), differential (faster restore than incremental). The 3-2-1 rule survives site loss. Recovery sites range from hot, through warm, to cold. RTO is time to recover, RPO is acceptable data loss; tighter targets cost more.

10F · Site security

Physical: perimeter, doors, mantraps and biometric access, with defence in depth for buildings. Environmental: gas-based fire suppression, cooling and humidity control, UPS and generators. Data destruction: overwrite, degauss, shred or cryptoshred, then verify recovery is impossible and keep chain of custody records. Asset lifecycle: acquire, assign, track, retire, destroy. A discarded drive is a breach waiting to happen.

Practical cautions

  • Do not treat CVSS score as risk; context decides priority.
  • Do not remediate false positives without validation.
  • Do not rely on non-credentialed scans alone; credentialed scans see missing patches.
  • Do not assume incremental backups restore fast; the chain is slow.
  • Do not confuse RTO (time) with RPO (data loss).
  • Do not assume all recovery sites are equal; hot, warm and cold differ in cost and downtime.
  • Do not run a penetration test without written rules of engagement.
  • Do not leave untested backups; they are hopes, not plans.
  • Do not discard a drive without verified data destruction and chain of custody records.

Core concepts

11A — Monitoring

Sources: logs (security, system, application, network device, firewall), flow (NetFlow/sFlow), packet capture, sensors, and the SIEM that aggregates and correlates them. Baselines define normal; thresholds alert on deviation; alert fatigue buries real incidents. Pair real-time alerting with trend analysis and tune alerts to cut false positives.

11B — Incident response

Six phases: preparation (before!), detection and analysis (confirm, scope, classify, grade severity), containment (evidence trade-off), eradication, recovery (validated restores, intensified monitoring), lessons learned. Classify each incident and set severity low to critical to drive urgency. Close with an after-action review and root cause analysis so the incident cannot recur.

11C — Forensics

Evidence must be admissible and lawful to collect (warrant or consent). Chain of custody: every handover documented. Order of volatility: registers, RAM, then disk — memory forensics often reveals what logs miss. Preservation: use write blockers, image and hash before analysis, apply legal hold, retain logs. Techniques: carving, timeline analysis, hash analysis, metadata analysis.

11D — Indicators

Malware: viruses, worms, Trojans, ransomware, spyware, rootkits, botnets. Network: port scanning, unusual traffic, data exfiltration, C2 beacons. Application: web log probes, phishing email, privilege escalation, privilege usage at odd hours. Behavioural: repeated failed logins, unusual times, impossible travel, data spikes.

Practical cautions

  • Do not start response at containment — preparation comes first.
  • Do not treat every incident alike — classify it and grade its severity.
  • Do not skip the after-action review — lessons learned prevent recurrence.
  • Do not analyse the original drive — image and hash first.
  • Do not collect evidence without authorisation — warrant or consent first.
  • Do not ignore the order of volatility — RAM will not wait.
  • Do not celebrate 'service restored' — verify and monitor.
  • Do not let alert volume hide the real incident.

Core concepts

12A — Governance

Policy states intent; standards set mandatory requirements; procedures give steps; guidelines advise. Documents form a hierarchy and run a lifecycle of develop, approve, distribute, review. Compliance: regulatory (law) vs industry (sector practice). Which apply depends on industry, geography and data types. Compliance sets a baseline — security must go beyond it for emerging threats.

12B — Risk management

Process: identify, assess, respond, monitor. Identification uses asset inventories, threat modelling and vulnerability assessments. Qualitative = ratings; quantitative = money (SLE = AV × EF; ALE = SLE × ARO). Responses: avoid, transfer, mitigate, accept — acceptance is documented, management-level. The risk register records risks, owners, ratings and treatment status, and is reviewed regularly. Vendor risk: assess before contract, monitor during, exit cleanly.

12C — Data protection

Classification: public, internal, confidential, restricted. States: at rest, in transit, in use. Roles: owner (accountable), steward (governance), custodian (implementation). Lifecycle with retention and secure destruction. GDPR/UK GDPR: principles, consent, rights, 72-hour breach duty. Sovereignty: jurisdiction follows the data and the data subject's location.

Practical cautions

  • Do not confuse policy (intent) with standard (requirements).
  • Do not treat guidelines as mandatory.
  • Do not accept risk without management sign-off and documentation.
  • Do not keep data beyond retention — destroy it securely.
  • Do not ignore which jurisdiction your cloud data lives in.
  • Do not swap the data owner (accountable) with the custodian (implementer).
  • Do not treat compliance as the whole of security — go beyond the baseline.
